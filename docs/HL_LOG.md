# HL（Heuristic Learning）迴圈紀錄

做法來自 Roy 的 wiki〈Heuristic Learning (HL)〉：**策略就是程式碼（`js/ai.js`）、用模擬回饋改它、舊能力用回歸測試固化**，不用梯度。
本專案的對應：

| HL 元件 | 本專案 |
|---|---|
| policy | `js/ai.js` 的 `chooseHard / chooseSuper / chooseExtreme` |
| state | `DEFAULT_HARD` 權重、`js/tables.js`（對手牌墩分布表）、`PRIOR_W` |
| feedback | `sim/` 的 duplicate 對戰、自我對弈取樣、連續多局實驗 |
| regression | `tests/engine.test.js`（AI 絕不倒水、列舉與暴力窮舉一致…）＋ `sim/` 的交叉驗證 |

下面記錄**每一輪實際做了什麼、數字是什麼**，包含走錯的路。

## 輪 1：超困難的對手分布表（`sim/calibrate.js`）

超困難要對「對手各墩牌力的分布」最大化期望得分，分布表本身要由 AI 自己的打法決定——是個不動點問題。

- **版本 A（失敗）**：每輪用「上一輪自己的打法」取樣更新表。跑 8 輪，新表 vs 舊表的 KS 距離卡在 ~0.11（頭墩 0.12、中墩 0.10、尾墩 0.05）不收斂；`super@新表` 對 `super@舊表` 每輪都贏 0.07–0.14 分／手。這是 best-response 來回擺盪，「新贏舊」只是因為它本來就是對舊表的最佳回應，**不代表進步**。
- **版本 B（採用）**：改成虛擬對局（fictitious play）：對手模型 = 歷代自我對弈分布的**等權混合**。跑 12 輪，KS 距離逐輪下降到 ≤ 0.004，`super@新表` 對 `super@舊表` 的得分趨近 0（第 12 輪：N=2 −0.005、N=3 +0.002、N=4 +0.020，每格 1500 副牌，詳見 `docs/calibration_log.json`）。

起點（第 0 輪）用的是調校前的「困難」打法；混合平均下它的權重只有 1/13。

## 輪 2：極限 — 先試蒙地卡羅，沒有增益，改走對手建模

原本的「極限」= 超困難的前 30 名候選擺法，對「從未見牌堆抽樣出的對手手牌」（對手用超困難擺）做 120 次情境模擬，選實際得分最高者。

- 10% 規模的試跑（`--scale 0.1`）：N=2 極限 vs 超困難 +0.017 ±0.076；N=4 極限 vs 三個超困難 −0.075 ±0.135。**統計上看不出比超困難強**，而且每手要算約 1 秒（瀏覽器端）。
- 探針（`sim/probe_adapt.js`）：如果超困難的對手模型直接換成對手**真實**的牌墩分布，對上困難 AI：N=2 由 +0.604 升到 +0.791，N=4 由 +1.940 升到 +2.497。對手模型貼不貼近對手，才是可以賺的地方。
- 決定：刪掉蒙地卡羅（YAGNI、慢、沒增益）；極限改為「超困難 ＋ 全壘打期望值 ＋ 逐局學習每位玩家的牌墩分布」。學習是**貝式收縮**：對手分布 = 先驗（超困難的表，等同 `PRIOR_W` 局）與觀察到的攤牌牌墩（每局權重 1）的加權混合；只用攤牌後的公開資訊，不偷看手牌。
- `PRIOR_W` 掃描（200 局 × 40 回合）：越小學得越快、但對上「已經是均衡打法的超困難」會輸一點（`PRIOR_W=8`：N=2 局 16–30 −0.102 ±0.045，顯著為負）；`PRIOR_W=40`：學習速度中等，對超困難不顯著變差。採用 40。

## 輪 3：困難的權重（`sim/tune_hard.js`）

困難 = 加權牌型分數 `wf·s(頭) + wm·s(中) + wb·s(尾)`。座標搜尋（每個參數 ×0.7 / ×1.4），候選對目前最佳做 duplicate 對戰，z > 1.5 才接受。

- 3 輪收斂：`{wf:1, wm:1, wb:1, r0:0.30, r1:0.05}` → `{wf:1.96, wm:0.7, wb:1.96, r0:0.42, r1:0.035}`（頭、尾墩權重高、中墩低）。
- 用全新牌局複驗（8000 副牌）：對調校前 +0.502 ±0.029（N=2）、+1.446 ±0.054（N=4）。
- 副作用：困難變強後，超困難 vs 困難的差距由 +0.57 縮到 +0.26 分／手（N=2）。

## 驗證用的「獨立實作」是怎麼確認它真的會抓錯的

交叉驗證若從不報錯，不能證明它有牙齒。所以刻意植入錯誤看它抓不抓得到（做完已還原）：

| 植入的錯誤 | 結果 |
|---|---|
| 同花裡鬼牌填 K 而非 A | `ref_eval.py` 報 313 / 13,014 不一致 |
| 取消 A-2-3-4-5 輪子順子 | 報 41 / 13,014 不一致 |
| 取消全壘打加倍 | `ref_score.py` 報 362 / 3,000 桌不一致 |
| 中墩五條加分 5 → 6 | 報 2 / 3,000 桌不一致（該牌型很少見，樣本少所以只有 2 桌） |

## 輪 4：外部審查（小o／Codex，唯讀）抓到的缺陷

送審範圍：`engine.js`、`ai.js`、`app.js`、`worker.js`、測試、README 聲稱與模擬輸出。審查者沒有找到牌型判定、計分、合法擺法列舉、座位對應、偷看手牌路徑上的錯誤，另有 3 條 confirmed、1 條 needs_validation，小c 逐條回原文核對：

| 發現 | 核對結果 | 處理 |
|---|---|---|
| 多人桌「極限」只算自己全壘打的收益，漏了「某位對手全壘打時，我對他的損失被加倍」 | 成立（`chooseExtreme` 只加 `HOMERUN_EXTRA*k*allSweep`） | 補上被全壘打的損失項：`−6 × Σ P(對手打槍我) × q^(N−2)`，`q`＝兩位實力相近玩家之間打槍的機率 0.11（取自對戰輸出：8079 / (1500×4×12)）；重跑對戰與連續多局，結果見 README |
| README 說「迭代到收斂」超出證據（KS 只看邊際分布、新舊表對戰≈0 不等於不可剝削） | 成立 | README 改成「迭代到穩定」並註明不是均衡證明 |
| 「對手越有固定偏好極限越賺」是過度概括（沒有量化固定偏好） | 成立 | README 改成只陳述測過的幾種對手 |
| needs_validation：對戰信賴區間是否以整副牌（duplicate 區塊）為獨立樣本 | 可由程式確認：`sim/lib.js` 的 `tourney` 以每副牌「各座位輪替後的總分」為一筆觀測，標準誤 = sd/√副牌數/人數 | 無須改動 |

審查者自陳沒檢查：`tables.js` 內容、校準與彙總程式、Python 交叉驗證、HTML/CSS、手機版面——這幾項由小c 另外驗證（見上方植入錯誤測試與瀏覽器實測）。

修正後的探針（未納入 `docs/tournament_output.txt`，指令 `node sim/tournament.js --n 4 --levels extreme,super,super,super --deals 4000 --seed 330000`）：極限（第一局、無學習）對三個超困難 +0.046 ±0.024；3 人桌 `--n 3 --levels extreme,super,super --deals 4000 --seed 331000`：+0.054 ±0.032。與修正前 +0.057 ±0.043（1500 副）一致，也就是這個項目在決策上影響很小，修正主要是讓目標函數與計分規則一致。
